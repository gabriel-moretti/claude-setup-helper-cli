# Governance — GitHub Free vs Enterprise

Ask which path applies: **Free public**, **Free private**, or **Enterprise** (GitHub Team/Pro private ≈ Free public for repo rulesets). Plans change — confirm against GitHub docs. Scripts need `gh` (authenticated) and Node.

## Common (any plan) — `governance/common/repo.sh OWNER/REPO`
Squash for work + merge commit for back-merges, PR title as squash message; variables `IN_PRODUCTION` (default false), `COVERAGE_MIN` 75, `COVERAGE_MIN_PROD` 85; environments `production` (only `v*` tags), `test`, `sandbox`. Going live: `IN_PRODUCTION=true governance/common/repo.sh OWNER/REPO`.

## Free — `governance/free/apply.sh OWNER/REPO`
| | Public | Private |
|---|---|---|
| Ruleset `main`: PR, code owners, squash, linear, required checks | ✅ | ❌ |
| Rulesets `test`/`sandbox`; `v*` tags only by Actions | ✅ | ❌ |
| Secret scanning + push protection | ✅ | ❌ (paid) |
| `production` environment approval | ✅ | ❌ |

**Free private limits** — no rulesets, so defense is layered: (1) lefthook hooks; (2) checks run on every PR but cannot block the merge button; (3) post-merge audit: `conventions` runs on every push to trunks and flags what slipped; (4) tags only from the workflow by team agreement. Say this plainly to the user; gitleaks/PAN still run in hooks and CI.

## Enterprise — org level
```bash
governance/enterprise/apply-org.sh ORG                       # properties + org rulesets; pattern rules in EVALUATE
governance/enterprise/set-repo.sh ORG/REPO in_production=false stack=node,python
governance/enterprise/set-repo.sh ORG/payments in_production=true pci_dss=true stack=python
# watch Org → Settings → Rulesets → Insights for 1–2 weeks, then:
governance/enterprise/apply-org.sh ORG --enforce
governance/enterprise/apply-org.sh ORG --enforce --required-workflows ORG/.github   # optional
```
Custom properties (`properties.json`): `in_production`, `pci_dss`, `stack` (node|python|flutter|php|docker|infra|docs), `criticality`, `hosting` — the last two mirror `standards.json`.

| Ruleset | Target | Rule |
|---|---|---|
| 01 Conventional branches | all repos/branches | `branch_name_pattern` (same regex as `lib/branch.cjs`, no AI prefixes) |
| 02 Gitmoji commits, no AI attribution | all | `commit_message_pattern` + negated AI pattern (covers web-edited squash) |
| 03 main · production | `in_production=true` | PR, 1 approval, code owners, last-push approval, squash, linear, required checks |
| 04 main · pre-production | `in_production=false` | PR, squash, `conventions` |
| 05 trunks | `test`, `sandbox` | PR, squash or merge, `ci-ok` + `conventions` |
| 06 version tags | `refs/tags/v*` | Actions only, immutable |
| 07 tag format | all tags | SemVer `tag_name_pattern` |
| 08 sensitive files | push, all | blocks `.env`, keys (`.pem`, `.key`, `.p12`…), `tfstate`, files > 10 MB |
| 09 PCI DSS | `pci_dss=true` | 2 approvals, signed commits |

Regexes are generated by `governance/enterprise/patterns.js` from `gitmojis.json` and `lib/branch.cjs`; rerun `apply-org.sh` when the gitmoji list changes.

**Rollout:** always evaluate → enforce. Evaluate mode also proves GitHub's regex engine accepted the patterns (not verifiable locally).

Required check contexts referenced by rulesets: `ci-ok`, `conventions`, `standards`, `release-check`, `pr-template`. Renaming any breaks every ruleset.
